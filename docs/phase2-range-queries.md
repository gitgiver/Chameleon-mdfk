## 1. 问题与定位

Chameleon 的叶子是 EBH 哈希表,键在叶内按 hash 位置散列存放,**没有任何键序**。因此范围查询
只能逐槽全扫:实现里 `range_query` 确实被写过,又被注释掉了(`Index.hpp`),因为对哈希叶而言
它就是"扫描每个触碰叶的全部槽位",没有意义。

本阶段问:**把叶子改成有序之后,范围查询能否从"不可用"变成"可用"?代价是什么?**

**定位**:这是基于 Chameleon 的**能力扩展**,对比对象是 Chameleon 自己的哈希叶(消融式比较),
不与 B+Tree / ALEX 等原生支持范围的索引比较(见 §6 局限)。

---

## 2. 实现

`Index::range_query(lo, hi, out)`(`index/include/Index.hpp`),两个自由函数递归实现:

- **走树**:内节点的孩子按**键区间有序**(数组下标即键序)。据此跳过区间完全在 `lo` 以下的
  子树(`interval.second <= lo`),并在遇到区间完全在 `hi` 以上的孩子时**提前终止**
  (`interval.first > hi`)。注意边界取半开语义:孩子的键落在 `[interval.first, interval.second)`。
- **有序叶**:键连续堆在槽位 `[0, size)` 且已排序 ⇒ 用 `std::lower_bound` 定位下界,再顺序前进
  直到第一个大于 `hi` 的键。
- **哈希叶**:逐槽检查(0..capacity),跳过空槽与区间外的键。**不能**因某个键大于 `hi` 而提前
  终止——槽序不是键序。

**输出语义**:有序叶按键序输出,哈希叶按槽序输出。调用方按**多重集**比较两者。

---

## 3. 负载构造与正确性

**构造:分位数法(主)**。每次查询取随机起点 `st`,令 `lo = D[st].key`、
`hi = D[st + s·n].key`,即区间**恰好覆盖数据集的固定比例 s**。这样结果大小在数据集之间相同,
是公平比较的前提。

> 键宽法(宽度 = 键范围的固定比例)会让结果大小随局部密度变化,本阶段未采用;它适合单独作为
> "密度偏置"负载,列为后续。

**正确性判据**。数据集在 bulk_load 前已排序,所以期望答案**恰好**是
`D[lower_bound(lo) .. upper_bound(hi))`。每查询比对结果大小;抽样前 200 条做**多重集逐元素**
比对(先按键排序,再与期望切片逐项比较)。

实测:四个数据集(uden / face / local_skew / mixed)、5 个选择性 × 2 种叶子形态 × 2 轮,
**全部 `errors=0`**。

**规模与协议**:n = 20M 键(`<double,double>`,数据本身 320 MB);结构钉死
`FIXED_CONF=256,16`、`TARGET_LEAF=1024`、`TARGET_FANOUT=16`;`PILOT_REPEATS=5`、丢首轮、
报各轮均值的最小值;`PILOT_EMIT_VOLUME=2e8`,使每轮测量时长落在 0.6~2.4 s(见 §5 测量教训)。

## 4. 结果

### 4.1 选择性扫描(两轮均值,ns/查询)

结构相同,唯一变量是叶子形态(哈希 / 有序)。四个数据集、五个选择性。

| 1e-4 | 2001 | 6957 | 8789 | 9053 | 7994 | 1.30× |

### 4.2 核心结论

**C1 有序叶的范围查询代价几乎与数据集无关,哈希叶的则不然。**

由 §4.1 两张表可得:

| | 有序叶 | 哈希叶 |
|---|---|---|
| 跨数据集差异(最大/最小) | **1.08× ~ 1.30×** | **2.23× ~ 3.27×** |
| 随选择性是否变化 | 否 | 否 |

四个分布完全不同的数据集(uden 连续整数 / face 密集低端切片 / local_skew 万个簇 /
mixed 均匀半段+簇状半段)都给出同一结论。

⇒ **可发表的表述**:有序叶**消除了范围查询延迟对叶子大小分布的敏感性**。加速比 6.6× 还是
2.2× 取决于数据/结构恰好把哈希叶拖到多差;而"有序叶的代价可预测、与结构无关"是稳定的。

**C2 机制(部分实测)。** 哈希叶回答范围查询必须扫满自己的 `capacity`,所以第一决定量是
**按大小加权的叶大小**(随机一个名次落在多大的叶里):

| dataset | 叶大小 p25/p50/p75/p99/max | **按大小加权均值** | ≤5 键占比 | 叶数 | 哈希 ns(s=1e-6) |
|---|---|---|---|---|---|
| local_skew | 15/81/135/773/1024 | **251.9** | 19.4% | 212011 | 3767 |
| uden | 305/305/305/306/306 | **305.2** | 0% | 65536 | 2257 |
| face | 37/114/284/930/1024 | **448.2** | 6.1% | 99931 | 5515 |
| mixed | 1/71/92/962/1024 | **634.4** | 26.9% | 128266 | 7140 |

叶大小解释了大部分排序(uden < face < mixed),但**不能解释全部**:local_skew 的按大小加权叶
大小最小(251.9),哈希延迟却是第二高(3767)。它的叶数是 uden 的 3.2 倍(212011),意味着树
更深。⇒ 决定哈希叶代价的是**叶大小 × 树深**两项,两者都随分布变化,而有序叶只取决于结果数与
`log(窗口)`,所以不受这两项影响。

**树深这一项目前是推断**(harness 未打印每查询内节点跳数,见 §6 局限 5)。

**C3 代价的分解。** 用窄端两点(s=1e-6 → 1e-5)拟合出固定成本与边际成本:

| | 固定成本(定位一次范围) | 边际成本(每个结果) |
|---|---|---|
| 哈希叶 | ≈ 2.14 µs | ≈ 3.6 ns |
| 有序叶 | ≈ 0.96 µs | ≈ 3.3 ns |
| 比值 | **2.2×** | 1.1× |

有序叶的优势几乎全在**定位**上,不在**输送结果**上 ⇒ 这就是为什么窄范围能快 5×、
宽范围只快 2.5×:宽范围里固定成本被淹没在输出里。边际成本随结果数增大而递减
(有序叶 3.33 → 2.11 ns/结果),宽端换算约 **6~7 GB/s**,哈希叶约 4.7 GB/s。

## 5. 测量教训(本阶段新踩的坑)

1. **"有序"档必须真的全有序。** 第一次跑 face 用了 `LEAF_WINDOW_THRESHOLD=16`,它在 face 上只
   转换 **26.2%** 的叶,于是测的是"全哈希 vs 1/4 有序"的混合体,加速比全是 1.0×。改用
   `WINDOW=1e9`(转换全部合格叶)后,face 的加速比变成 4.9~5.1×。**判据档位不等价于叶子形态档位。**
2. **测量时长决定可复现性。** 发射预算 2e7 时,中间档每轮只有 70~90 ms,同一配置两轮差
   13~34%。提到 2e8 后(每轮 0.6~2.4 s),10 格里 8 格收敛到 ≤5.3%。
3. **仍有 1 格系统性不稳**:`s=1e-2` 的**有序叶**,四个数据集全部如此(两轮差异
   uden 12.2%、face 15.1%、local_skew 1.9%、mixed 7.9%)。原因与第 2 条不同——它每轮要吐
   约 3 GB 结果,**带宽受限**,受内存子系统状态影响,且是该形态独有(哈希叶在同一格只有
   0.1%~2.6% 的差异,因为它不做二分定位)。曲线引用时应截到 `s ≤ 1e-3`,或明确标注该格为
   带宽受限。
4. **脚本的两个疏漏**:未 `cd` 导致 harness 自己的结果表落到仓库根;删除每轮 stdout 导致分布
   打印丢失。均已修(`scripts/sweep_range.sh`)。

## 6. 局限性

1. **数据集全部是 20M 切片,且都不是各自全量分布的代表**(见第 4 条);四个数据集的分布类型
   差异很大(连续整数 / 密集低端 / 万个簇 / 半均匀半簇),这支持"跨分布稳健",但**不能替代**
   在真实全量数据上的验证。
2. **无外部基线**:对比对象只有 Chameleon 自己的哈希叶,没有 B+Tree / ALEX / PGM。因此只能说
   "比原来的哈希叶快",不能说"比主流范围索引快"——后者很可能不成立(B+Tree 本就为范围查询
   设计)。
3. **重复键完全未覆盖**:四个数据集实测都**没有重复键**(uden 是连续整数;face / local_skew /
   mixed 的 20M 条记录去重后条数不变)。因此重复键下的行为——同一键占多个槽、oracle 的多重集
   比较是否仍然成立——完全没有验证。
4. **20M 都是切片**:uden 取自 200M 的前 20M(连续整数 ⇒ 完美均匀);face 取自 **最小的 20M**,
   落在全量键范围 [1, 1.84e19] 的**前 4.1e-10**,切片内呈"紧密簇 + 簇间大空隙"。两者都不是
   各自全量分布的代表。
5. **机制中"树深"部分是推断**:harness 未打印每查询内节点跳数,所以"某个数据集的树更深"只有
   叶数作为间接证据(local_skew 212011 叶、是 uden 的 3.2 倍,但按大小加权的叶大小最小、
   哈希延迟却第二高)。补一行内节点跳数的打印即可闭环。
6. **只读负载**:有序叶目前**没有插入路径**(`find_insert` 仍走哈希,对有序叶会静默写坏结构),
   故全部为只读。范围查询 + 更新需要先实现有序插入/删除。

## 7. 与阶段一的关系:场景矩阵

把两阶段的结果并起来,叶子形态是一个**按场景选择**的旋钮:

| | 点查为主 | 范围为主 |
|---|---|---|
| **只读 / 内存敏感** | 哈希叶(保持现状) | **有序叶** |
| **有更新** | 哈希叶 | 有序叶 + 尾隙(未实现) |

关键约束(来自阶段一):**有序叶对纯点查工作负载永远不划算**——即使理想情形(uden,预测逐个
精确)也是 +19~20% 延迟。因此判据不能只有"窗口 ≤ τ",还需要**工作负载维度**:只有存在范围
查询时,转换才值得。这既是"拓宽应用场景"的准确表述,也是它成立的前提。

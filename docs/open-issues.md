## A. 测量方法与负载构造

### A1 范围查询的**结果条数被固定了**

- **问题**:真实范围查询(如 `[100, 500]`)返回的条数**不固定**,取决于查询落在哪、以及数据的局部密度。当前构造是 `span = s·n`(以**名次**为宽度),每次查询**恰好返回 `span+1` 条**。也就是说:测的是"选择性 = s"这一类查询,不是"任意真实区间"。
- **现状**:所有范围数据(`results/logs_prod*/`)都出自这种构造。它给出的是 **`cost(结果条数)` 曲线**;任何 workload 的平均延迟可由曲线按该 workload 的选择性分布加权得到 `E[cost] = Σ p(s)·cost(s)`。
- **要解决**:再加一种**键宽构造**——宽度固定为**键值范围**的固定比例(`hi = lo + w·(kmax−kmin)`),结果条数随局部密度自然变化。harness 里换一种生成 `lo/hi` 的方式即可,改动小。

### A2 查询**落点分布**未覆盖

- **问题**:当前按**名次**均匀抽样起点 ⇒ 均匀落在键上。真实 workload 的落点可能聚集(例如"最近一个月")。
- **现状**:未测。在偏斜数据上这一条影响可能很大:整段落在稠密簇内的区间,与横跨稀疏区的区间,代价结构不同。
- **要解决**:加一种"落点受限"的构造(例如只在最大的叶子/某个密集区域内抽起点)。

### A3 运行间噪声 ~3%,跨条件必须配对

- **问题**:同一配置换一次运行,范围延迟可摆动 **3.2%**(osmc@50M 同配置三次:4,328,527 / 4,446,609 / 4,467,438 ns)。跨条件**不配对**比较会把符号测反——实测过:完整扫描里 τ=4 报"慢 0.35%",改成交替配对后三对**全是快 0.15%~3.7%**。
- **现状**:`scripts/sweep_prod.sh` 是逐档顺序跑,不配对;点估计用 min-of-passes,只消除**轮内**干扰,消除不了**跨运行**差异。
- **要解决**:比较两个条件时交替重复跑(off, τ, off, τ, …)取配对差;或在报告里把 ≤5% 的差标为"不可分辨"。

### A4 `PROD_QUERIES` 会改变范围查询集

- **问题**:harness 的范围起点从 `rng(1000)` 抽取,而抽之前先跑点查阶段;点查消耗的随机数个数 = `PROD_QUERIES`。所以**改了 `PROD_QUERIES` 等于换了另一批范围查询**。
- **现状**:同一批实验内 `PROD_QUERIES` 一致,成对比较有效;但跨批次(如 40M 那批 vs 8M 那批)的绝对值**不可直接比**。
- **要解决**:把范围起点的 RNG 与点查阶段的 RNG 分开(两个独立 generator)。

## B. 判据设计

### B1 判据的转换量强烈依赖数据集

- **读数**(n=50M,同一门限 τ=4):logn 内存降 **−34.1%**、uden **−34.8%**;face 只降 **−0.27%**、osmc **−0.23%**;face 要到 **τ=1e9** 才降 −34.5%。
- **现状**:无统一定量解释。已知窗口(p99 排名预测误差)是**绝对槽位数**、随叶大小增长。
- **要解决**:给出"数据集特征 → 需要多大 τ"的可测判据;或在报告里把 τ 作为每个数据集各自的超参报告。

### B2 决策单位是"整片叶"+ p99

- **问题**:一片叶内只要有一小部分聚集,p99 就爆掉 ⇒ 整片被拒,而叶内**局部均匀的小块**无法被单独转换。
- **现状**:未验证、未处理。
- **要解决**:把判据从"接受/拒绝"改成"**分裂规则**"(判据不过且叶仍够大 ⇒ 按确定性规则切开重判)。代价:会改动树的结构。

### B3 分位数的选择未探索

- **问题**:用 p99 很严。换成 p90 或均值会转换更多叶,但尾部查询的代价变大。
- **现状**:只用 p99。未做对比。

## C. 实现与工程

### C1 有序叶**没有插入/删除路径**

- `find_insert` 仍走哈希,对有序叶调用会写坏结构。**当前全部实验都是只读**。
- 要解决:实现搬移插入(尾隙 + shift),或"被写操作触及即重建回哈希叶"。

### C2 `CB`(重训线程)与有序叶不兼容

- `random_rebuild` 用 `find_insert` 重建 ⇒ 会把有序叶**悄悄改回哈希叶**;且它假设树正好三层,对 RL 的深树会把 inner node 当 data node 用。只读场景下 `CB` 本来关闭。
- 要解决:编译期 guard;或把重建改为调 `build_leaf_`(顺带实现"叶形随漂移重判")并使区间锁支持任意深度。

### C3 建索引是"逐节点一次 GPU 前向"

- **读数**:时间 ≈ 节点数 × ~0.5 ms。50M face:28.7 万叶 ⇒ 147 s;50M logn:44.5 万叶 ⇒ 252 s;50M osmc:177 万叶 ⇒ 83 s(叶多但节点小)。
- **现状**:纯工程开销,不影响任何决策。**这不属于本工作引入的开销**——判据关闭时 `build_leaf_` 与原始实现工作量相同。
- **要解决**:把同一节点的一批孩子打包成一次 forward(或按层 BFS 批处理),30 万次调用可压到几次。

### C4 `leaf_id` 与逐叶诊断已在 `PILOT_DIAGNOSTICS` 下隔离

- 已完成:诊断默认关闭,生产构建无 `leaf_id`(省 8 字节/叶),且查询路径不写共享状态。**范围查询函数本来就不写共享状态**。

## D. 数据与基线

### D1 无外部基线

- 对比对象只有 Chameleon 自己的哈希叶。**没有 B+Tree / ALEX / PGM**。仓库里没有 `others/` 目录。

### D2 数据集都是切片,且 n 未统一

- uden 取前 N 条连续整数(连续整数 ⇒ 完美均匀);face / logn / osmc 取各自**最小的 N 个键**,不代表全量分布。
- 已统一到 n=50M 的:uden、face、logn、osmc。face 另有 20M / 100M(残缺)/ 200M(仅 τ=1e9 完整)。
- face@100M / 200M 的结构出现极端情形(root=1~2、叶巨大),范围档无法在合理时间内跑完。

### D3 重复键完全未覆盖

- 四个数据集实测都**没有重复键**(去重后条数与记录数相同)。

### D4 2M 尺度的数字一律不可用

- 2M 与 20M 的智能体结构完全不同(face:2M ⇒ root=151/53,999 叶;20M ⇒ root=5/1,363 叶)。任何 2M 结论不可外推。
